# 0.8.0 连接与恢复架构修正记录

日期：2026-09-09。UI 0.8.0，执行器 0.4.1。测试环境为 Linux；未把模拟 GitHub 测试写成真实 GitHub 或 Windows 验收。

## 修正目标

- 不依赖某位用户的全局 Git 配置：插件先使用系统默认连接；只读版本查询遇到暂时连接错误时，后续有限重试才使用进程内 HTTP/1.1。不会修改全局配置。
- 只读 Git 与 GitHub API 最多尝试三次；创建、推送和其他可能产生外部写入的命令只执行一次。
- 请求记录包含目标仓库、工具、操作、阶段、次数、起止时间、耗时、协议模式、结果和错误类别，不保存完整命令、原始错误输出或凭据。
- 新计划在首次写入前完整核对；恢复时只核对下一步涉及的父仓库和子仓库，后续每一步在写入前再核对自身依赖。最终验收仍检查全部目标。
- 创建请求返回后先保存仓库 ID、归属 ID 和完整名称，再独立核验远端；只有身份完全一致才自动接续。没有精确创建回执时，不凭同名自动接管。
- 本地生成、暂存和提交阶段先保存“已执行、未核验”，不依赖额外联网。推送响应丢失时，只有远端提交恰好等于已保存本地提交且其他状态不变才接续。
- 旧版接续预览读取固定提交的 commit/tree/blob 对象，不再克隆仓库；用户确认时只复核身份、权限和分支提交。
- 页面增加只读连接检测，分别报告账号接口、远端版本与临时浅克隆；任务关闭后入口自动禁用。

## 实现中发现并修正的回归

- 阶段检查点最初与已批准计划共享内存对象，可能导致记录进度时改变计划内的“创建前状态”，进而漏生成 LICENSE。改为深拷贝，并验证批准计划文件字节保持不变。
- 删除每步结束的远端查询后，发现它曾顺带修正本地规则快照。现在本地阶段直接完整继承基线规则，挂载和刷新也明确保存本地阶段。
- 本地测试仓库首次推送 README 后缺少阶段核验，导致下一步把远端提交误判为变化；新增 initialized 阶段。
- 已完成任务的 current.repo 是“全部目标仓库”，不能用作连接测试目标；现改为使用真实总入口。

## 测试结果

Python 测试共 78 项，按套件运行并通过：implementation 17、GitHub 模拟 10、partial recovery 9、recovery 10、UI 8、reliability 8、registration 4、survey 6、transport 6。

其中覆盖：审批后漂移阻止首次写入、操作间外部文件阻止、创建回执身份不符拒绝、下载断开保留残留、推送成功但响应丢失不重复提交、未知旧执行器拒绝迁移、原计划不变、只读请求有限重试、写入不重试、请求记录不含原始凭据、完成任务连接测试不创建仓库。

浏览器测试 16 项通过，证据见 `reliability-080/browser-result.json`。测试使用模拟接口，没有真实 GitHub 写入。一次旧浏览器二进制启动 SIGSEGV，重新下载同版本浏览器后测试通过；该次启动失败不计为产品功能通过证据。

技能结构快速校验、Python 编译、JavaScript 语法和 `git diff --check` 均通过。`.quanttide/asset/contract.yaml` 仅把技能版本登记为 0.4.1，资产登记结构与规格文件未改变；本轮未重新编译 Rust CLI，原生 CLI 证据仍以 trial-011 为准。

## 尚未完成的验证

本轮未操作用户 sample3、未真实写入 GitHub、未在 Windows 实机恢复、未在公司组织测试。因此 0.8.0 是待实机验证的候选版，不应描述为所有同事均已稳定使用。网络完全不可用、创建请求成功但响应完全丢失且无创建回执、未知本地残留或远端存在额外提交时仍会暂停，要求人工核对。
