# 0.8.4 通用连续创建与中断恢复

日期：2026-09-10。UI 0.8.4，执行器 0.4.5。

## 本轮为什么不是修 sample4

用户提供的 0.8.3 诊断记录显示：sample4 的 27 项计划已完成 17 项，暂停于领域仓库的第 5 个配套仓库挂载。六个配套仓库均已在本机完成下载、提交和远端核验；失败命令却是 `git submodule` 再次访问同一 GitHub 仓库。账号接口与远端版本读取可以成功，下载数据通道不稳定。

根因是旧实现把两件事绑定在一起：一是把子仓库提交登记进父仓库，二是再次从 GitHub 下载子仓库。领域越多、挂载越多，不必要的网络失败点越多。这与 sample4 名称无关，继续增加 sample5、sample6 只会重复暴露同一结构问题。

## 通用修改

- 计划内子仓库先按原流程创建或读取、提交并核验；父仓库挂载时从已核验的本机子仓库物化工作树和 Git 指针，只在 `.gitmodules` 保存公开 GitHub URL。
- 挂载中断后，仅允许恢复同一计划中的当前挂载。程序核对父子仓库身份、远端提交、本机提交、来源和工作流文件范围；一致才补记完成并继续。
- 首次仓库下载失败时使用新的隔离目录有限重试，不删除失败残留、不覆盖目标目录。推送仍不盲目重试；先通过提交与远端检查点判断实际结果。
- 只读 GitHub API 在没有收到明确 HTTP 响应时有限重试；明确 404、认证或权限结果不伪装成网络成功。
- 暂停页按无方案、已确认未完成、全部操作完成、版本或现场变化显示唯一主要入口，并给出三步恢复方案。诊断包降为无法安全自动判断时的最后证据。
- 0.4.4 的精确执行器 SHA-256 已加入兼容表，因此 sample4 原计划、确认和日志不需要改写。

## 结论与剩余验收

实现方向回到任务核心：将原始对话流程与章程整理为资产云登记的可复用技能和可运行配置，让非技术用户在中文页面中反复创建、看懂计划、核对产物，并在中断后安全继续。程序不能保证互联网永不失败，也不能自动覆盖他人修改；工程标准是减少不必要的网络操作、保存可验证检查点、对不确定写入先核验，并为每种可识别状态给出页面内恢复方案。

剩余一项真实验收：在用户电脑用 0.8.4 打开原 sample4 记录，点击“自动核对并继续”，确认无需改名重建即可完成剩余操作和最终远端检查。通过后再用两个全新名称连续创建，保存 GitHub 仓库链接、提交号和人工体验意见。
