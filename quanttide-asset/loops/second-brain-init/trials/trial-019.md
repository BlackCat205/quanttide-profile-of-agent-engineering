# 0.8.5 推送恢复与当前状态纠正

日期：2026-09-11。UI 0.8.5，执行器 0.4.6。

## 输入证据与根因

用户上传的 0.8.4 诊断包表明，旧第 18 项挂载已经恢复，流程继续完成至第 21 项；当前失败为第 22 项领域仓库推送。已形成本机提交，工作区干净，尚未取得本次推送完成的确认。随后账号接口、远端版本检测通过，Git 下载检测失败。不能由此确定 HTTP/2、代理或具体网络设备是唯一原因。

确认的产品缺陷：连接检测把执行错误覆盖为“检测完成”；暂停页同时突出历史首次失败，隐藏实际当前推送失败。下载、只读查询、推送的恢复策略不一致；线程重启清空兼容策略；一般恢复入口先于文件变化等阻塞原因判断。

## 通用修改与边界

- 分离当前错误和折叠历史；旧记录若已被“检测完成”覆盖，从执行日志读取实际错误。后续连接检测保留当前错误，并分别保存三项检测结果和时间。
- 执行下载与诊断下载共用隔离目录和三次上限。保留失败目录，不覆盖目标工作目录。同一任务从请求记录恢复 GitHub HTTP/1.1 兼容偏好，仅作用于插件进程。
- 推送锁定确切的本机提交。每次写入前核对仓库身份、权限、分支、有效推送地址、干净工作区、本机提交和远端基线；使用普通非强制推送，保留 Git 对并发更新的拒绝机制。
- 推送后无论命令成功还是网络异常，均重新读取远端：已经收到则完成；未收到且基线不变才允许兼容重试，最多三次；远端不可读则停止写入。遇到其他提交或目标变化不自动合并、覆盖或重建。
- 现场变化优先给出维护者处理说明。明确权限或执行锁问题给出先处理、再核对的入口，不删除锁或自动获取权限。
- 新版本仍兼容已登记的旧执行器哈希；未修改任何旧计划或确认。契约的 6 个资产及技能结构不变，仅更新技能和 UI 版本号。

原有 94 项回归均通过；新增 10 项恢复测试均通过。结果来自完整回归与针对测试夹具修正后的定向复测，不宣称最后一次完整测试进程零错误。

第二次完整运行的唯一错误来自新测试使用了 `test` 作为运行编号，未满足工具原有的 16 位十六进制编号校验。改为合法夹具编号后，新测试组全部通过；这次仅修改测试数据，没有修改被测产品代码。

首次完整回归执行 103 项，102 项通过、1 项失败：隔离下载重构改变临时目录前缀，旧恢复测试无法找到预期位置的失败残留。已恢复兼容前缀，并添加连接检测保留当前错误的集成测试后重跑。

新增测试覆盖：失败后同一提交有限重试、推送完成但回执丢失、持续中断三次停止、远端读取不明时不重试、并发远端提交阻止写入、推送目标变化阻止写入、旧检测提示不能隐藏当前失败、兼容任务的文件变化/锁/权限分类、任务重开恢复连接偏好、API 通过而 Git 失败时保持创建错误。

资产入口检查为本仓库 `asset-entry.py check`，不是再次运行原生 Rust CLI 的证明。契约登记的原生 CLI 历史证据继续见原测试记录。

## 真实环境验收

本轮自动化在 Linux 环境执行，Git 提交/推送使用真实本地 bare 仓库，GitHub API 与断网通过模拟注入。Windows 文件占用测试属于故障模拟，不是 Windows 实机运行。本轮没有从该环境创建真实 GitHub 第二大脑仓库，也没有得到用户电脑上 0.8.5 完整成功的证据。

升级后先恢复原任务，核对最终仓库链接、提交号、查询时间与逐条标准。之后在同一测试入口连续建立不同名称的领域，确认旧领域保留。断网时必须保留提交和进度并明确待核验，联网后可从原任务核对恢复；人工内容/导航/可用性验收仍须如实填写。
