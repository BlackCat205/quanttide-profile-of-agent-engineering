# 0.9.0：按使用流程升级可靠性

日期：2026-09-14。UI 0.9.0，执行器 0.5.0。

## 问题范围

历史诊断记录覆盖 sample3、sample4、sample5，暴露了四类共性问题：辅助请求日志被 Windows 占用会影响任务页面；多个启动窗口只在单进程内互斥；远端写入前缺少统一的关键凭据保存闸门；页面未把本地成果、远端同步、技术核验和人工验收分开呈现。网络故障仍可能发生，但程序应保留成果、准确说明状态并限制重试。

## 实现

- 关键执行计划、确认记录与执行日志读取失败时禁止新的远端写入；损坏记录保留原件，不按空记录重建。
- 请求诊断日志降为辅助信息。读取或写入失败时显示警告，主任务仍依据关键记录运行，不覆盖旧日志。
- GitHub 建仓或推送前先持久化写入意图；保存失败时外部命令尚未调用。
- 使用操作系统文件锁协调重复启动器、不同进程和同一 GitHub 总入口；进程终止后内核释放锁。旧 PID 锁仅在确认进程不存在后接续。
- 错误记录增加类别、操作、尝试次数和时间。Git 传输连续失败三次后先检查下载通道，不再直接循环推送。
- 页面增加“创建第二大脑／继续已有任务／查看成果与报告”入口、记录搜索和逐仓库成果状态；恢复记录在任务列表中归入接续后的记录，原记录仍保留。
- 0.8.6 的已确认计划保持原计划编号、确认记录与操作范围，可由 0.5.0 执行器继续。

## 自动化验证

完整回归运行 125 项：124 项通过，1 项因当前 Linux 环境不具备 Windows 文件共享 API 而跳过。通过项目包括：

- 实际本地 Git 的 27 项完整创建、连续四领域创建及最终核验；
- 建仓成功但回执丢失、推送响应丢失、远端并发修改、挂载中断；
- 关键记录写入失败后在原任务恢复，未重复提交；
- 请求日志不可读时任务完成且旧日志未覆盖；
- 双进程互斥、重复启动器复用现有服务、进程强制结束后释放锁；
- 同一 GitHub 总入口跨工作区互斥；
- 0.8.6 计划保留原确认和范围继续；
- 未完成任务也能显示八个目标仓库的成果与同步状态。

同时通过 Python 编译、JavaScript 语法、Git 差异格式、技能结构和插件侧 `.quanttide` 契约入口检查。

## 验证边界
