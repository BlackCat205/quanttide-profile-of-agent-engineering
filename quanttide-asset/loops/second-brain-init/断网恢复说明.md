# 断网后如何继续

先保留原任务、原仓库和本机工作空间，不需要换 sample4 重建。

如果记录显示 `execution-plan.json` 不存在，说明中断发生在方案形成之前，尚未开始创建或推送。这类记录在 0.8.3 中只显示“重新生成方案”；点击后沿用原内容重新调查。只有进入方案核对页并再次人工确认后，才会执行写入。

## 旧版 sample3 任务

1. 关闭旧启动窗口，解压新版，双击“启动向导.bat”。沿用原来的保存位置。
2. 从“最近记录”打开 sample3 暂停任务，点击“检查接续方案”。此操作读取远端与本机，尚不提交代码。
3. 页面会展示账号、仓库名称、仓库 ID、提交版本、初始 README。确认这些确实是你允许接续的仓库，填写核对人姓名并勾选确认。
4. 点击“确认并生成恢复任务”。检查完成后点击“打开已生成的恢复任务”，再点击“检查并继续”。
5. 完成创建后查看结果页。技术检查与人工验收都通过，才算本轮验收完成。

接续入口只支持已知旧执行器、建立仓库步骤中断、其他仓库没有变化、目标只有一次初始提交且只有标准 README、本地尚未下载的情况。它不能证明历史创建归属，因此需要本人核对并明确允许接续。原计划、原确认和原执行日志保留；恢复任务另存，继续使用同一工作空间。

若出现其他文件、额外提交、残留本地目标目录或身份变化，停止接续并导出诊断包，不删除文件、不强制推送。

## 新版创建任务

日志会显示“远端仓库已创建”“已下载到本机”“已保存生成文件”“已准备提交”“本地提交已保存”“远端提交已核对”。这些是阶段记录；总操作数仍表示计划操作，不能与阶段条数相加。

下载在工作空间的 downloads 文件夹内独立进行，成功后才移到 repositories。失败的下载残留保留在 downloads，不影响另一次下载，也不会自动删除；未完成的残留不算已创建产物。

点击“检查并继续”会核对已保存的检查点与实际状态。若上次推送已成功但响应丢失，只有远端恰好等于已记录的本地提交、身份和其余状态全部相同时才接续；不会重复提交。

页面保留首次执行失败及最近检查结果。反复读取失败时，导出诊断包。诊断包不含需求正文、仓库正文或登录凭据。

## 仍可能暂停的情况

网络故障发生在阶段凭证保存前、远端创建请求成功但响应完全丢失、提交过程中断、已有文件/仓库被他人修改等情况，仍需要维护者核对。不会仅凭同名或网络恢复就自动认定安全。新版本不能修好本机网络；Windows 实机及你的 sample3 恢复结果仍需实际试用确认。


## 0.8.0 更新

暂停任务可先点击右侧“检查 GitHub 连接”，分别查看账号接口、远端版本和下载连接。检测会在临时目录下载，结束后清理；不提交代码，也不修改全局 Git 配置。检测通过不等于创建验收通过。

Git 远端读取遇到暂时连接错误时，会在后续有限重试中尝试 HTTP/1.1。成功后本次后台操作的后续 Git 命令沿用该模式；下一次操作重新检测。不自动重试推送。

本地文件、暂存和提交阶段不再逐次联网。操作完成证据先保存，远端复核单独进行；失败会保留“已执行、未核验”的记录，而不是抹去中间成果。此状态仍需核对，不会无条件再次写入。

旧任务接续预览改为读取固定提交的 GitHub commit/tree/blob 对象，不再克隆；确认仍复核版本。其他原有接续条件不变。0.7.0 执行器任务不能直接跨版本继续；请保留记录由维护者核对，不要手工修改版本哈希。原 sample3 的 0.3.1 接续入口继续可用。

诊断记录显示具体仓库、操作、时间、次数和兼容模式。请求日志最多保留最近 2000 条，不包含完整命令参数、原始错误输出或凭据。

## 0.8.1 更新

GitHub 仓库身份、默认分支提交和标签统一通过登录后的 GitHub API 核验，不再为了执行前检查重复调用 `git ls-remote`。Git 数据通道仍用于必须传输仓库内容的克隆、子模块更新和推送；连接检查会继续分别展示两类通道，便于判断故障位置。

若 0.8.0 已保存“已下载到本机”“已保存生成文件”“已准备提交”或“本地提交已保存”阶段，0.8.1 会先核对远端身份与提交、本地分支和来源、工作流文件哈希、变更路径或提交父节点。完全一致才记录为已恢复并继续；出现额外文件、额外提交或来源变化仍会暂停。

0.8.0 的执行计划仅以已登记的精确执行器哈希进入兼容范围，计划正文、用户确认和既有日志不会被改写。其他未知版本仍必须走专用审阅入口。

## 0.8.2 更新

Windows 可能因杀毒扫描、文件索引或两个短时写入靠得太近而暂时占用 JSON 文件。记录器现在为每次写入创建唯一临时文件、对同一路径串行写入，并在 `PermissionError / WinError 5` 时短暂重试；不会再共享固定的 `requests.json.tmp`。

请求日志和验收进度属于辅助观察。即使辅助记录在重试后仍无法写入，也只记为 `local-file-busy`，不能改变 GitHub 请求、创建、推送或最终核验本身的结果。执行计划、确认、检查点和执行日志仍是关键记录；关键记录无法原子保存时继续暂停，避免无记录写入。

若执行日志已经显示全部 27 项完成，而最终报告尚未生成，应使用结果页“重新检查”。此操作只重新读取本地与远端结果，不再创建仓库或推送。
